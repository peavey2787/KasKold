# Reproducible release builds

KasKold 2.0.0 pins the material release-build inputs and builds signed and
unsigned firmware artifacts separately. The production firmware target is the
hardware-qualified **M5Stack CoreS3**. CoreS3 Lite reuses the same hardware
adapter and partition geometry, but it is build-supported only until physical
qualification is complete; it is therefore not emitted as a production release
target.

An unsigned production image exists for reproducibility comparison only. It has
no valid production signature and is not a deployable release image.

## Public build interface

Use the repository Make facade:

```bash
make release
```

The target performs the pinned host prefetch, immutable toolchain-image
construction, network-disabled Docker build, artifact export, and manifest
verification through the platform implementation helpers. It does **not**
require external audit/HIL/signing-custody attestations merely to reproduce the
artifacts.

Before publishing a production release, run the separate fail-closed evidence
gate after the artifacts exist:

```bash
make release-readiness
```

That command requires the operator-controlled evidence bindings documented in
[`qa/release/README.md`](../../qa/release/README.md).

## CoreS3 artifact set

An unsigned reproducibility build emits:

- `kaskold-m5stack-unsigned.bin`
- `kaskold-m5stack-unsigned-full.bin`
- `kaskold-m5stack-unsigned.codehash`
- `kaskold-m5stack-partitions.csv`

When a signing key is supplied through the supported Docker secret path, the
release additionally emits:

- `kaskold-m5stack.bin`
- `kaskold-m5stack-full.bin`
- `kaskold-m5stack.codehash`

The release directory also contains the source/build-input manifests and
`SHA256SUMS`. Compare unsigned artifacts only with the published unsigned
artifacts from the same source/build-input manifest. Never compare a local
unsigned image against a signed release image.

To build the signed and unsigned set:

```bash
make release SIGNING_KEY=/path/to/signing_key.bin
```

Optional public parameters include `RELEASE_DIR=/path/to/output` and
`REFRESH_INPUTS=1`. The signing key remains an input to the Docker secret path;
it is not embedded into the toolchain image.

## Partition identity

`kaskold-m5stack-partitions.csv` is the canonical CoreS3 partition table. The
release manifest binds it by SHA-256 and records the OTA application geometry
and final persistent-state reservation. CoreS3 Lite deliberately shares this
same flash layout; that compatibility does not constitute hardware
qualification or authorize a Lite production release artifact.

## Five-pass convergence

Each release configuration builds and hashes five times. Generated
hash/signature bytes are fixed-size `static` objects in flash `.rodata`, and
firmware loads them through volatile reads so LLVM cannot materialize those
generated bytes into the executable segment being hashed. The build requires
**passes 2 through 5** to produce the same executable code-segment hash. One
final build is then made from the converged `firmware_hash.rs`.

The final ESP application image is parsed independently of `gen-hash` and must
match the generated code-segment **address, byte length, and SHA-256**.
Ambiguous images containing more than one flash-mapped code segment are
rejected. The physical HIL path uses the same convergence step and fails closed
if the running mapped segment does not match the embedded hash before a HIL PASS
marker is accepted.

Boot cryptographic known-answer tests are included in release configurations.
`skip-tests` is forbidden together with `production`/`silent`.

## Published hashes

Do not copy historical artifact hashes into this guide. The authoritative hashes
for a KasKold release are the `SHA256SUMS`, source manifest, and build-input
manifest exported by that exact reproducible build. This avoids presenting
hashes from an earlier product, hardware matrix, or source revision as current
KasKold release evidence.
